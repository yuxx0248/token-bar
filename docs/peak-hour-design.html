0TL;DR

  • Peak 官方定义：周一至周五 14:00–18:00，UTC+8（新加坡时间）；其余时间（晚间、清晨、周末）均为 off-peak，消耗减半。
  • quota/limit 接口不返回 peak 信息（已实测），需在 app 内内置静态规则 + 促销期覆盖表。
  • 菜单栏标题在百分比之后追加状态图标：peak 🔥 / off-peak ❄️（推荐 SF Symbols flame.fill / snowflake，橙 / 青双色）。
  • 下拉菜单新增「Peak 时段」小节：当前状态 + 倒计时、换算成本地时区的时段、计费倍率说明。
  • 注意：今天（10-06）落在官方促销期 2026-09-25 ~ 10-07 全天 off-peak 内，实现后上线即会命中该覆盖分支，正好可以验证。

1背景与官方事实

1.1 计费规则（来源：docs.z.ai）

项目规则
Peak 时段 周一至周五 14:00–18:00 新加坡标准时间（UTC+8，无夏令时）
Off-peak 时段 其余全部时间：工作日 00:00–14:00 与 18:00–24:00、周末全天
倍率（GLM-5.3） peak 3× / off-peak 1×
倍率（GLM-5.3-Flash） peak 1.2× / off-peak 0.4×
促销覆盖期 2026-09-25 ~ 2026-10-07（UTC+8）全天按 off-peak 计费

1.2 接口现状（已实测）

实际调用 GET /api/monitor/usage/quota/limit，返回中只有 level 与 limits[]（5h / 周窗口），没有任何 peak 相关字段； 本地 ZCode 客户端代码里的 peakHour 是统计页"最活跃小时"，与计费无关。

结论：peak 规则无法从 API 获得，按「内置静态规则 + 可覆盖的促销期列表」实现。 规则集中放在一个 PeakPolicy 常量区，官方改时段时只改一处。

1.3 语义澄清

标题图标回答的问题是「此刻消耗的是不是 peak 倍率」，而不是"现在是不是 14–18 点"—— 两者在促销期会分离（促销期内即使是 14–18 点也按 off-peak 计费，图标应显示 off-peak）。 下拉菜单里再展示日历意义上的时段和促销说明。

2交互设计

2.1 菜单栏标题（直接显示）

现有：⚡ + 5h 百分比 + · + 周百分比。在百分比之后追加一个 peak 状态图标（与配额数字留一个空格），颜色语义与现有百分比着色体系一致（暖 = 贵/危险，冷 = 便宜/安全）：

🔋 100%📶 ⚡ 16% · 5% 🔥
peak 状态（工作日 14:00–18:00 UTC+8）：橙色 flame
🔋 100%📶 ⚡ 16% · 5% ❄
off-peak 状态（其余时间 / 周末 / 促销期）：青色 snowflake
  • 图标放在末尾：紧跟配额数据之后，读作「当前窗口消耗处于什么档位」，也不与开头的 ⚡ 品牌位挤在一起。
  • 宽度代价约 14pt，菜单栏可接受；图标不参与交互（菜单栏整块本来就是按钮）。
  • mockup 中以 emoji 示意，实际实现首选 SF Symbols（见 §3），颜色可精确控制。
  • 数据未加载（快照为空、显示模拟数据）时：仍显示 peak 图标——peak 判定是纯本地计算，不依赖网络，这是把它做进标题的底气。

3图标方案与推荐

方案peak / off-peak优点缺点
A · SF Symbols flame.fill 🔥 / snowflake ❄ macOS 原生观感，12pt 锐利，粗细与菜单栏匹配；可任意着色（橙 / 青），暗色模式可控 需 NSTextAttachment + 着色 helper（约 30 行） ✅ 推荐
B · Emoji 🔥 / ❄️ 零代码，自带彩色 颜色不可控、跨系统渲染不一致、宽度偏大、暗色菜单栏上偏"跳" 备选
C · 文本符号 ▲ / ▽（着色） 最极简，宽度最小 ▲/▽ 容易误读为"用量涨/跌"，语义错位 不推荐
D · SF 昼夜对 sun.max.fill / moon.stars.fill 直觉的"白天/夜晚" 语义错误：peak 是工作日 14–18 点；off-peak 包含工作日白天（如上午 10 点 ❓） 不推荐
E · SF 闪电对 bolt.fill / bolt.slash "耗电快/慢"隐喻贴切 与 app 自身的 ⚡ 前缀重复，两个闪电图标并排易混淆 不推荐

推荐理由（方案 A）

  • 语义最准：peak = 配额烧得快（3×），"火焰"是最直接的隐喻；off-peak = 价格冷却，"雪花" + 冷色。
  • 颜色系统一致：橙（systemOrange）/ 青（systemTeal，与现有走势图同色）构成暖冷对比，半秒可读。
  • 菜单栏友好：SF Symbols 在 12pt 下经过 Apple 调优，比 emoji 干净；着色后深浅菜单栏都成立。

着色实现要点

/// 用 NSTextAttachment 把着色后的 SF Symbol 嵌进 attributedTitle
func peakIcon(state: PeakState) -> NSAttributedString {
    let name  = state == .peak ? "flame.fill" : "snowflake"
    let color = state == .peak ? NSColor.systemOrange : NSColor.systemTeal
    let att = NSTextAttachment()
    if let img = NSImage(systemSymbolName: name, accessibilityDescription: nil)?
        .withSymbolConfiguration(.init(pointSize: 11, weight: .semibold)) {
        att.image = img.tinted(with: color)          // 小 helper：bitmap 重绘着色
        att.bounds = CGRect(x: 0, y: -2, width: 12, height: 12)  // 基线对齐 12pt 文本
    }
    return NSAttributedString(attachment: att)
}

4技术设计

4.1 数据模型

enum PeakState { case peak, offPeak, promoOffPeak }

struct PeakStatus {
    var state: PeakState
    var localWindowText: String   // 换算到本地时区的时段描述，如 "周一至周五 14:00–18:00"
    var nextChange: Date?         // 状态下次切换时刻（peak 结束 / 下个 peak 开始 / 促销结束）
    var nextChangeLabel: String?  // 如 "18:00 结束" / "下一 peak 10/7 14:00" / "10/8 00:00 恢复"
    var note: String?             // 促销备注，如 "促销期全天 off-peak"
}

/// 官方规则集中地 —— 官方调价时只改这里
enum PeakPolicy {
    static let tz = TimeZone(identifier: "Asia/Singapore")!   // UTC+8，无夏令时
    static let startHour = 14
    static let endHour   = 18
    static let weekdays: Set<Int> = [2, 3, 4, 5, 6]           // Calendar.weekday：1=周日
    static let rateNote  = "off-peak GLM-5.3 1× · Flash 0.4× ｜ peak 3× · 1.2×"

    /// 全天 off-peak 的促销覆盖期（SGT 挂钟时间；start 闭、end 开）
    static let promos: [(start: Date, end: Date, note: String)] = [
        (date("2026-09-25 00:00"), date("2026-10-08 00:00"), "促销期：全天按 off-peak 计费"),
    ]
}

4.2 判定算法（纯本地、O(1)）

func evaluatePeak(now: Date = Date()) -> PeakStatus {
    var cal = Calendar(identifier: .gregorian)
    cal.timeZone = PeakPolicy.tz                       // ① 一律在 SGT 日历里判定，
    let c = cal.dateComponents([.weekday, .hour], from: now)  //    本地时区/夏令时完全不影响正确性

    // ② 促销覆盖优先于常规时段
    if let p = PeakPolicy.promos.first(where: { now >= $0.start && now < $0.end }) {
        return PeakStatus(state: .promoOffPeak, ..., nextChange: p.end,
                          nextChangeLabel: "…恢复", note: p.note)
    }

    // ③ 常规判定：工作日 & 14 ≤ hour < 18
    let inWindow = PeakPolicy.weekdays.contains(c.weekday!)
                && c.hour! >= PeakPolicy.startHour && c.hour! < PeakPolicy.endHour

    // ④ nextChange：peak → 今日 18:00；off-peak → 从 now 起向前逐日找
    //    下一个「工作日 14:00」（最多 7 次迭代），再套 fmtDuration 生成倒计时文案
    ...
}

4.3 本地时区换算（显示）

换算只影响展示，不影响判定。取本周周一~周五 5 个 SGT 窗口 （weekday 14:00 ~ weekday 18:00），逐一转成本地 Date 再格式化；5 个本地区间形制相同时压缩成一条范围。

本地时区换算结果（示例）说明
Asia/Shanghai（UTC+8）周一至周五 14:00–18:00与 SGT 同偏移，恒等
UTC周一至周五 06:00–10:00整点偏移，同日
Asia/Kolkata（UTC+5:30）周一至周五 11:30–15:30半小时偏移，同日
America/Los_Angeles（UTC-7 夏令时）周日至周四 23:00–次日 03:00 跨午夜 + 星期整体前移一天；跨日端需 (+1d) 后缀
必须程序化换算、不能写死本地字符串：偏移 ≥ 15h（西侧）时窗口跨午夜且星期平移。 另注意本地时区若有夏令时，换算结果会随 DST 切换漂移 1 小时——每次刷新重算即可（现有 5 分钟数据刷新 + 30s 渲染刷新已覆盖）。判定逻辑始终在 SGT 进行，不受影响。

7后续与开放问题

  • 官方改时段怎么办：目前规则写死在 PeakPolicy（集中一处）。若未来官方在 API 里暴露 peak 字段（或发布订阅接口），替换数据源即可，UI 层不动。
  • 促销期维护：新促销活动需手动加进 promos；结束日期过后自动失效。
  • 菜单栏宽度：若未来再加信息导致标题过宽，优先考虑把 peak 图标与 ⚡ 合并成一个复合图标（peak 时整体变橙）。
  • 「下个 peak 提醒」（如提前 15min 用户通知）：可作为 P2，用 UNUserNotificationCenter，默认关闭。
